# Security

## This library has not been audited

dcr-rs has had no independent security audit. It implements Decred's byte
formats and key derivation against dcrd's source and is pinned by vectors taken
from dcrd and by a real mainnet transaction. That pins the formats; it does not
make the library safe to hold significant value with. Read the code before you
trust it with money.

What "checked against dcrd" does and does not mean:

- **Does mean:** BLAKE-256, BIP32 chains under both derivation variants and
  most address vectors are compared against output of dcrd's own code. The
  signature hash has no dcrd vector: it is checked by requiring a real mainnet
  transaction's signatures to verify against the sighash this crate computes.
  [Correctness](README.md#correctness) in the README says exactly what each
  vector set covers.
- **Does not mean:** the library is free of memory-handling, timing, validation
  or logic bugs, that the covered surface is complete, or that anyone has
  attacked it. The vectors are committed fixtures; CI does not regenerate them
  against dcrd.

## Reporting a vulnerability

Email **jz@jz.bz**. Please do not open a public issue for anything that could
affect funds.

There is no bounty and no formal SLA. Expect an acknowledgement within a few
days.

A defect that could affect funds is fixed in a new release first. The affected
versions are then yanked and a [RustSec](https://rustsec.org) advisory is filed,
so `cargo audit` flags it for anyone still on one. A yank does not break an
existing `Cargo.lock`; the advisory is what reaches those builds.

## Threat model and known limits

### Key material is wiped on drop, not protected in memory

`ExtPrivKey` secrets and chain codes, and BIP39 mnemonics, are overwritten on
drop. BIP32 HMAC outputs, the BIP39 seed this crate expands, and the buffers
used to serialize and parse `dprv` strings are overwritten once used. None of
that reaches copies made elsewhere: a value a by-value call has already
copied, the internal state of the HMAC-SHA512 and PBKDF2 implementations that
process seeds, mnemonics and parent secrets, or the `dprv` string `to_base58`
returns, which is the caller's to wipe. It shrinks the window; it does not
close it.

### No constant-time guarantees for Decred-specific code

Curve operations come from libsecp256k1 through the
[`secp256k1`](https://crates.io/crates/secp256k1) crate, which documents its own
side-channel properties. This crate's own code (BLAKE-256, base58check
checksums, serialization, comparisons) is not written to be constant-time, and
the base58 codec, from [`bs58`](https://crates.io/crates/bs58), makes no
constant-time claim either; it handles the raw secret whenever a `dprv` string
is encoded or decoded.

### An extended private key's round trip can change its hardened children

Decred's hardened derivation depends on whether a key is stored with its leading
zero bytes stripped, and a `dprv` string cannot carry that. A key parsed back
from its own `dprv` can therefore derive different hardened children than the
key it was serialized from. This mirrors dcrd; `ExtPrivKey::from_base58`
documents it. Where a wallet's hardened descendants must be reproduced, derive
from the seed.

### Untrusted input

Base58 strings are length-gated before the quadratic decode, airgap packages are
capped at `airgap::MAX_PACKAGE_BYTES` (512 KiB), and the transaction parser
rejects hostile counts, non-canonical varints and trailing bytes. A device with
little RAM should impose its own, far lower, package limit before decoding.

### Airgap interop

The golden bytes for airgap format version 3 are generated by this crate.
Interop with the KeyOS and Keystone encoders is unverified until they emit
version 3.

### Overflow checks are the application's call

Amounts are summed in exact `i128` and each is capped at max supply, so this
crate does not rely on overflow checks. Build signing firmware with
`overflow-checks = true` in `[profile.release]` anyway: a library's own profile
is ignored when it is a dependency.

### Out of scope

Networking and RPC, staking, mixing, and transaction-construction policy (coin
selection, fees, change). Only P2PKH inputs under SigHashAll are signed.

## Supported versions

Pre-1.0: only the latest release gets fixes.
